# 2.0 人球识别：训练机执行任务单

- **任务状态**：正式执行指令
- **下发日期**：2026-10-30
- **项目**：2.0 人球识别 / 基础动作识别与事件定位
- **工作目录**：训练机上的 2.0 项目副本
- **上游文档**：`2.0人球识别_阶段总结与后续规划.md`
- **执行原则**：先审计、后验证、再决定是否训练；不得用单次高分替代证据

## 一、任务目标

本轮工作的首要目标不是继续堆叠模型，而是回答三个问题：

1. 当前 2.0 基线、数据划分、评测和部署链路是否可复现；
2. BallFused 在检测球输入而非 GT 球输入下是否仍然有效；
3. 哪些问题可以由机器独立解决，哪些问题必须等待人工补标注、人工确认或独立比赛数据。

所有新结果必须能追溯到数据版本、代码版本、checkpoint、配置、运行命令和日志。

## 二、硬性边界

1. 不删除、覆盖或改写 2.0 已有权重、日志、配置和失败实验。
2. 新实验使用独立目录，例如 `runs/2_0_followup_20261030/`，不得混入旧结果目录。
3. 不把尚未运行的方案写成已完成结果。
4. 不使用独立测试集选择模型、调阈值或改规则。
5. GT 球轨迹结果与检测球轨迹结果必须分开报告，禁止混为同一结论。
6. 关键对照至少使用 3 个随机种子；单次运行只作为调试结果。
7. 差异小于 5 个百分点先标为噪声，必须结合置信区间或多 seed 后再下结论。
8. 不自行补标注、改标签、录制比赛或替代项目负责人作标注决定。
9. 未经本任务单授权，不新增大型模型、不引入复杂新分支、不开展无目标的大规模重训。

## 三、执行顺序

### 阶段 0：环境与资产盘点（先做，不启动大规模训练）

检查并记录：

- Python、PyTorch、CUDA、Ultralytics、OpenCV 版本；
- 检测、跟踪、分类、BallFused、解码和评测的实际入口文件；
- 数据集目录、视频划分、标注文件、类别映射和帧率；
- 现有 checkpoint、`args`、`results.csv`、概率落盘、部署配置和日志；
- 2.0 基线与后续实验目录之间的对应关系。

输出：

- `reports/2_0_followup_20261030_asset_inventory.json`
- `reports/2_0_followup_20261030_audit.md`
- `reports/2_0_followup_20261030_repro_commands.txt`

审计报告必须列出：已完成实验、缺失资产、疑似配置不一致、潜在数据泄漏、不能复现的结果和建议优先级。

### 阶段 1：数据与评测审计

在不修改人工标签的前提下完成：

- 按视频、类别、轨迹和 clip 统计样本量；
- 统计事件数量、持续时间、边界和帧率；
- 检查训练/验证/测试视频是否有重叠或时间泄漏；
- 检查类别映射、时间戳、XML/JSON 读取和缺失值；
- 复核当前 mTAP、tIoU、帧级 Macro-F1、Micro-F1 和 bootstrap 实现；
- 检查重复预测的一对一匹配、容差单位、track ID 匹配和事件边界处理；
- 自动生成疑似异常标注清单，但不得自动改标签。

输出：

- `reports/2_0_followup_20261030_dataset_stats.json`
- `reports/2_0_followup_20261030_eval_audit.md`
- `reports/2_0_followup_20261030_annotation_review_queue.csv`

报告中要明确区分“代码发现的问题”“数据发现的问题”和“需要人工判断的问题”。

### 阶段 2：BallFused 真实输入鲁棒性验证（本轮核心任务）

使用现有可复用数据和 checkpoint，先做离线验证，不要立即重训大模型。

建立以下输入条件：

1. GT 球轨迹；
2. 现有检测球轨迹；
3. 检测球轨迹 + 现有 fill/interpolation；
4. 检测球轨迹 + 人为模拟漏检；
5. 检测球轨迹 + 轨迹位置抖动；
6. 按可见率或连续性划分的低、中、高质量输入。

对 R(2+1)D、MViT 和 BallFused 保持相同视频、相同 clip、相同解码和相同评测口径，比较：

- clip 级逐类 Precision、Recall、F1、Macro-F1；
- 完整视频帧级 Macro-F1；
- 事件级 mF1@0、mF1@10、mTAP@0、mTAP@10；
- `pass`、`shoot`、`dribble`、`defense` 的单类变化；
- 球轨迹可见率、连续长度、抖动幅度与识别性能的关系；
- FPS、端到端耗时和显存。

重点回答：BallFused 的收益是否只存在于 GT 球输入；`pass` 的方向性收益能否迁移到检测球；哪一类球输入质量会使 BallFused 失效。

输出：

- `reports/2_0_followup_20261030_ball_input_quality.csv`
- `reports/2_0_followup_20261030_ballfused_robustness.md`
- `reports/2_0_followup_20261030_ballfused_examples/`
- 所有运行日志和配置文件

每个输入条件至少保留一个可复现命令。若现有数据或脚本不足以生成某一输入条件，记录缺口并停止扩展，不得伪造结果。

### 阶段 3：检测、跟踪与图块质量定位

仅在阶段 0–2 完成后执行。使用现有视频和结果，分析：

- 球员漏检、误检和球检测连续性；
- ByteTrack / OC-SORT 的 ID Switch、轨迹中断和遮挡恢复；
- 球员图块裁剪是否偏移、截断或包含过多背景；
- 检测帧率、分类帧率和轨迹缓冲之间的关系；
- 跟踪错误是否与 `pass`、`defense` 失败相关。

能计算时报告 HOTA、IDF1、ID Switch、轨迹连续率和图块有效率；不能计算时说明原因，不用替代指标冒充标准结果。

输出：

- `reports/2_0_followup_20261030_tracking_quality.csv`
- `reports/2_0_followup_20261030_tracking_failure_analysis.md`
- 代表性失败视频或帧的可视化目录

只有在证据显示跟踪错误是主要瓶颈时，才提出 ReID 或其他复杂跟踪改动。

### 阶段 4：低风险解码复核

在已有概率输出上完成离线对照：

- argmax；
- 逐类峰值检测；
- 时间 NMS；
- 双阈值滞回；
- 事件合并和碎片抑制；
- 现有 `nodef` / `nodrib` 语义门控；
- 以上方法在 R(2+1)D、MViT 和 BallFused 上的组合差异。

必须同时报告帧级与事件级指标，并保留每类预测事件数、漏检数和过报数。若已有 2.0 结果已经充分覆盖某配置，不重复训练，只做复核或注明“已有结果足够”。

输出：

- `reports/2_0_followup_20261030_decode_grid.csv`
- `reports/2_0_followup_20261030_decode_analysis.md`
- 解码配置、概率输入和完整日志

### 阶段 5：条件式训练任务

只有满足以下任一条件，才进入训练：

- 阶段 2 证明检测球输入下 BallFused 明确失效，且存在可自动构造的训练输入；
- 阶段 3 证明图块或轨迹质量是主瓶颈，并且修复方案已有清晰实现；
- 项目负责人后续明确授权某项新模型或消融。

允许的优先顺序：

1. 检测球轨迹质量模拟训练；
2. GT/检测球混合质量训练；
3. pass 时序增强；
4. SoftIC 或其他针对长尾问题的消融。

训练要求：

- R(2+1)D、MViT、BallFused 至少保留一个可靠基线；
- 同一数据划分、预处理、epoch、优化器和评测脚本；
- 至少 3 个 seed；
- 使用独立输出目录和分离任务启动方式；
- 每个实验写明假设、对照、预期判据和停止条件；
- 若结果低于 5pt 或置信区间重叠，结论写为“未观察到可区分提升”。

未满足触发条件时，阶段 5 只输出训练建议，不启动重训。

本轮任务完成必须交付：

1. 资产与环境盘点；
2. 数据和评测审计；
3. BallFused GT/检测球输入对照；
4. 跟踪和图块质量分析；
5. 解码复核结果；

总报告必须回答：

- 当前最可信的帧级和事件级基线是什么；
- BallFused 是否在真实输入下成立；
- 当前最大瓶颈属于数据、标签、检测、跟踪、分类还是解码；
- 哪些差异属于噪声；
- 下一步是否值得训练，以及训练的唯一明确假设是什么；
- 需要项目负责人提供哪些人工输入，数量、格式和用途是什么。

## 五、人工输入清单（训练机不得代做）
